# Book style

This note is for anyone editing the maintainers' book in `book/`. It restates the rules in [README.md](README.md) and sets the book's chapter shape and voice. The code stays the source of truth; the book describes what it does.

## Audience and scope

The book is for GoAkt maintainers and contributors, as [README.md](README.md) states. It explains the current implementation: data structures, algorithms, concurrency and invariants.

It is not user documentation and does not prescribe a future design. Do not add an explanation, guarantee, limitation or rationale unless the current code, its comments or an enforcing test establishes it.

## Truth and checks

- Name symbols and files: `` `PID.tryPassivation` in `actor/pid.go` ``. Do not cite line numbers.
- Call something a **guarantee** only when a test enforces it. Put the statement in the **Guarantees** table with the test function and file.
- Put defaults, pools, heuristics and other changeable choices under **Implementation details (may change)** unless a test locks them.
- Put operational edges and surprises under **Behaviours to know**. Keep the failure path next to the behaviour it affects when readers need it to understand the mechanism.
- Take rationale only from an explicit code comment. If the code does not state why it works that way, document the behaviour without guessing at its reason.
- Do not generalise from a name, an API shape or a familiar design pattern. Trace every statement to the current implementation, a code comment, or an enforcing test.
- After heading or cross-reference edits, run `python3 book/tools/toc.py` and `python3 book/tools/linkrefs.py`, then `make book-check`.

## Three layers

- **Map.** [architecture.md](architecture.md) explains the whole system: its main flows, consistency model and glossary. A flow has a diagram when useful, a short explanation and links to the chapter that owns its detail.
- **Tour.** [chapters/chap-01.md](chapters/chap-01.md) and [chapters/chap-02.md](chapters/chap-02.md) explain the model, repository, build and test setup. Their section titles are thematic rather than numbered. Chapter 2 has no Guarantees table.
- **Deep dive.** [chapters/chap-03.md](chapters/chap-03.md) onwards each explain one subsystem. They use numbered `## N.M` sections and the closing sections below.

Chapters 1 and 2 stay thematic. Chapters 3 through 27 use `N.M` in section titles so § references stay stable (`linkrefs.py`).

## Chapter skeleton (3 through 27)

```text
# N. Title
## Contents                 ← regenerated by toc.py
## What you will learn        ← five to seven outcome bullets
## Scope                      ← optional; two to four sentences on what this chapter owns and what it defers
## N.1 …
## N.2 …
…
## Guarantees
## Implementation details (may change)
## Behaviours to know
## Further reading             ← optional; use for sources named in code comments
```

**What you will learn** lists outcomes: "how a turn ends", "which lane a control request takes". It is not another table of contents. Defer out-of-scope topics in one sentence with a chapter link (see [Chapter 5](chapters/chap-05.md) before §5.1).

**Scope** is worth adding when the chapter borders another (for example dispatch versus mailboxes, or grain engine versus grain process).

Headings and Contents entries are reader-facing navigation. Write type, feature and API names there as plain text: `## 14.4 GrainContext`, not ``## 14.4 `GrainContext` ``. Use inline code in the body where the text refers to the declared identifier.

## Writing a section

Start with the result a reader should retain. Then explain enough mechanism to establish it. Put configuration, races and failure paths in short subsections or bullets when they would interrupt the main explanation.

Name the code immediately after the statement it supports: `` `Name` in `path/file.go` ``. Use a table only where the reader is comparing alternatives or properties. Use Mermaid where order, state or concurrent ownership is easier to see than to read. Do not redraw or restyle an existing diagram for editorial consistency alone; change it only when it is inaccurate, unclear enough to obstruct the explanation, or no longer matches the implementation.

Keep test names out of the mechanism prose. They belong in **Guarantees** (or in [architecture.md](architecture.md) when the overview states a concurrency property and names its test).

**Spacing:** Give each paragraph one main idea. Prefer two or three short sentences to one long chain of clauses. Break a paragraph when it begins to combine the mechanism, its rationale, and an exception or consequence; each deserves its own paragraph when separating them makes the explanation easier to follow. A numbered step list may be longer when sequence is the subject. Define a specialist term at its first meaningful use in a chapter, or link straight to its definition.

## Voice and typography

**Use**

- Present tense, third person: "The dispatcher owns…", "A send returns…".
- British spelling (`behaviour`, `serialise`, `cancelled`). The linter whitelists these ([Chapter 2](chapters/chap-02.md)).
- Plain verbs and concrete subjects. "The worker takes an actor" is clearer than an abstract description of the operation.
- Colons and full stops. Split long chains into separate sentences.
- Cross-links: `[Chapter 7, §7.5](chapters/chap-07.md#75-the-ready-queue)`.
- Tables for comparisons (send families, flags, ports).
- Mermaid for flows, state and sequence.
- Blockquotes sparingly for fixed warnings (`> **Warning for contributors.**` in [Chapter 1](chapters/chap-01.md)).

**Avoid**

- Em-dashes.
- Filler that delays the point.
- Second person except in the contributor callouts above.
- Stating a guarantee in prose without the matching test in the Guarantees table.

## Callouts

- Use a `> **…**` blockquote for one fixed rule a reader must not miss, such as the pointer-actor rule or a contributor warning.
- Use a bold label at the start of a bullet for a distinct subtopic inside a long section, such as `**Tell.**` in an architecture flow. When the label is a named feature, use plain bold text: write **TrySchedule**, not **`TrySchedule`**.
- Use the Guarantees table for a contract that the test suite enforces.

Do not add Mintlify-style components here; the book is plain Markdown.

## architecture.md

Each entry under **Key data flows** should be:

1. Mermaid diagram (when the flow is not obvious from one sentence).
2. One or two short paragraphs, or a tight bullet list when steps are the point (grain activation).
3. A **Detail:** line with links to chapter sections. Step-by-step prose belongs in the chapters, not in the overview.

Design decisions, concurrency, startup, cluster consistency, extension points and the glossary stay in architecture.md as reference sections.

## Review before verified

Read a changed chapter against the current implementation before keeping its verified status.

- Check every behavioural statement against the named symbol and file.
- Check every guarantee against the named test.
- Check that headings and Contents entries use reader-facing plain text.
- Check that bold marks reader-facing emphasis rather than inline code.
- Check that each diagram has nearby prose stating the behaviour it shows.
- Check that tables compare concise facts; move narrative prose into paragraphs.
- Check that dense paragraphs separate the mechanism from its rationale, exception or consequence when doing so improves the explanation.

## Measured facts

Counts, versions and similar measurements describe the repository only when their source is named. State the command, file or configuration that provides the fact. Recheck such facts against the current repository whenever the source changes; do not retain a number because it appeared in an earlier revision of the book.

## Status

A chapter marked **verified** in [README.md](README.md) has been read against the code and its guarantees against the named tests. When code changes, run `make book-affected` and re-read the listed chapters before keeping verified status.
